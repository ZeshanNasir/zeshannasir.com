01 / THESIS

The Reliability Manifesto

Four practical principles for grounding AI in truth and running dependable systems.

01 / INPUT QUALITY

Fix the source data, not just the prompt.

An AI assistant cannot reason past stale documentation, conflicting runbooks, or broken APIs. When source data has clear owners and automated checks, hallucinations disappear at the source.

“Clean inputs before clever prompts. Truth in, truth out.”
02 / DOCUMENTATION

Treat documentation like code.

Undocumented systems cannot be safely automated. Documentation is the contract both human teams and AI agents rely on. It needs the same discipline as code: automated linting, review schedules, and deprecation.

03 / GOVERNANCE

Unowned pages rot.

Without an assigned owner and an expiration date, enterprise wikis fill with conflicting instructions. Automated systems must identify neglected pages and remove them from AI search indexes.

04 / OWNERSHIP

Own your infrastructure.

Cloud dashboards hide how systems actually behave under stress. Running physical hypervisors, tuning CPU inference for local models, and routinely testing bare-metal restores provides real operational understanding.

“If you haven't tested a restore from scratch, you don't have backups—you have hopes.”

SYSTEM 01 Enterprise Automation · Knowledge Governance · AI Grounding

Enterprise Knowledge Lifecycle Governance

Knowledge Workspace API Workflow Automation Service Management API Enterprise Search Python

An automated engine that audits enterprise documentation, assigns page owners, schedules reviews, and archives stale pages so AI assistants only read verified truth.

The Problem

As enterprise AI assistants were rolled out, a large share of indexed documentation had no identifiable owner and no review date. Unowned pages produce conflicting instructions, and an AI assistant grounded on them repeats the conflict with complete confidence.

What I Built & Enforced

Architected an automated validation pipeline connecting enterprise workflow engines with knowledge workspace APIs. Every page must define an owner and a review cadence (90 to 365 days). Daily jobs check review dates and open tickets for page owners. Pages that are not reviewed are moved to an archive and removed from the AI search index.

Why It Matters

Transformed an unmaintained wiki into a verified knowledge contract. AI assistants and enterprise search query only active, reviewed documentation, eliminating hallucinations caused by stale internal pages.

What the design enforces

Every page in a governed space carries an owner and a review cadence, or it does not stay in the index.

How deprecation works

Obsolete pages move to an unindexed archive rather than being deleted, so inbound links resolve instead of breaking.

SYSTEM 02 Local AI · Supervised Automation · Systems Reliability

Hermes: Supervised Infrastructure Agent

Local Model Engine MCP Architecture Human-in-the-Loop Prometheus / Loki Proxmox VE

A private, local operations agent that diagnoses cluster anomalies and drafts remediations, with strict human approval gates for every system modification.

The Problem

Giving autonomous AI agents direct command-line access is dangerous—hallucinations during an incident can trigger cascade outages. Conversely, purely read-only bots cannot assist with complex remediations.

What I Built & Hardened

Engineered a 6-step operational safety loop: Clarify → Inspect → Draft → Preview → Approve → Log. Hermes diagnoses issues by comparing real-time logs and metrics against structured cluster documentation. All state-changing actions (restarts, configuration edits, firewall changes) require explicit human approval on a rendered diff before executing.

Why It Matters

Proves that local AI can safely assist with production infrastructure operations without leaking private data, incurring cloud API costs, or risking unapproved system modifications.

The safety property

No state-changing command executes without a human approving a rendered diff first. The gate is structural, not a policy the agent is asked to follow.

What it actually does

Reads metrics and logs across the cluster, correlates an anomaly to a probable cause, and drafts the remediation for review.

SYSTEM 03 Hypervisors · High Availability · Hardware Isolation

OMEGA Cluster: Resilient Multi-Node Platform

Proxmox VE 8.x Corosync QDevice ik_llama.cpp WireGuard OPNsense Proxmox Backup

A resilient two-node physical cluster with an off-site cloud tie-breaker, dedicated CPU model serving, and verified daily recovery drills.

The Problem

Running local AI inference alongside background automation causes CPU thread contention and latency spikes. In addition, standard two-node clusters risk split-brain lockups when one server reboots for maintenance.

What I Engineered

Added an external cloud tie-breaker (Corosync QDevice) over an encrypted WireGuard tunnel, establishing an independent 3-vote quorum outside the local network. Configured ik_llama.cpp on dedicated CPU cores with pinned threads and Flash Attention, ensuring consistent inference speed while background automation runs.

Why It Matters

Enables rolling host maintenance without guest downtime, and provides predictable local AI performance on commodity hardware without dedicated GPUs.

Quorum topology
2 + 1 nodes plus witness

An external Corosync QDevice outside the local failure domain breaks the tie, so either node can reboot without freezing cluster state.

Inference tier

Dedicated CPU compute with Flash Attention and quantized KV caching, isolated from background ingestion pipelines.

04 / DECISION RECORDS

Architectural Tradeoffs

Measured engineering decisions made on production systems. Tradeoffs over dogmas.

ADR 01 · CLUSTER RESILIENCE

External Cloud Quorum Witness

Context & Tradeoff

A 2-node cluster cannot distinguish between a node failure and a network split. A reboot for routine maintenance risks freezing cluster state.

Decision

Deployed a lightweight Corosync tie-breaker daemon on an off-site cloud VPS over an encrypted WireGuard tunnel, outside the local failure domain.

Result

Either physical server can reboot for maintenance without interrupting cluster services or risking split-brain.

ADR 02 · COMPUTE OPTIMIZATION

CPU Inference Optimization via ik_llama.cpp

Context & Tradeoff

Dedicated GPUs add high hardware costs and power draw. Standard CPU inference experiences latency spikes when background tasks run.

Decision

Configured ik_llama.cpp on dedicated CPU cores with pinned threads, Flash Attention, and quantized KV caching to isolate AI workloads from background jobs.

Result

Fast, predictable response times on host CPU compute, eliminating external API costs, data leaks, and discrete GPU lock-in.

ADR 03 · AUTONOMOUS SAFETY

Read-Only Triage with Gated Mutations

Context & Tradeoff

AI agents with unconstrained shell access risk executing destructive commands during outages. Read-only bots cannot help execute fixes.

Decision

Hermes has read access to logs and telemetry to diagnose anomalies, but all state-changing commands require human operator sign-off on a diff before running.

Result

Fast anomaly detection and troubleshooting with zero risk of unapproved configuration drift or accidental outages.

ADR 04 · DISASTER RECOVERY

Recovery as a Continuous Engineering Contract

Context & Tradeoff

Backups that are never tested usually fail when an emergency strikes.

Decision

Automated daily chunk-deduplicated snapshots to an isolated Proxmox Backup Server, backed by documented, tested bare-metal restore drills.

Result

Tested, repeatable recovery runbooks that restore any guest to running state with predictable recovery time.
